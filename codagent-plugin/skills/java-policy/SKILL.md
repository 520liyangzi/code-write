# Java Policy

只使用已激活的规则库。不要把原始规范全文读入上下文，也不要把候选规则描述成已生效规范。

## 编码流程

1. 将一次方法、类、配置或紧密相关的多文件修改视为一个“逻辑改动单元”。
2. 第一次写入前，按任务、目标文件、代码/API 特征检索规则。先读取 [主动检索命令](references/runtime.md)，在能够取得真实会话 ID 并调用命令时主动生成一次性 receipt。无法取得会话 ID 或无法执行命令时不得伪造；让 `PreToolUse` Hook 拒绝第一次写入并返回规则，向用户报告后再重试。外部 Hook 超时属于宿主边界，不能声称它提供操作系统级 fail-closed。
3. 检索失败时停止写入并如实报告；不得凭记忆声称符合公司规范。
4. 命中规则时按规则 ID 实施；未命中时可采用项目现有模式和 Java 21/Spring MVC 通用实践，但必须明确说明“已检索，无专门规范”。
5. receipt 只能用于对应目标和一次写入，不得复用来绕过后续查询。每个逻辑改动单元写入后，处理 Hook 返回的问题；阻断问题未解决前不得继续或结束任务。
6. 结束前调用 `java-review` 的流程审查完整变更。

不得通过 Shell 重定向、Python/Node 写文件脚本或会修改源码的外部命令绕过 Edit/Write Hook。受管文件必须使用 `Edit`、`Write` 或 `MultiEdit` 修改；运行只读搜索、编译和测试命令不受此限制。

## 实时追踪

在每个逻辑改动单元写入前简要报告：

```text
[规范追踪｜写入前]
目标：<文件、类或方法>
规范检索：已完成 / 失败
命中：<规则 ID，或“无专门规范”>
实施依据：已批准规范 / 项目现有模式与通用实践
CodeGraph：已使用 / 跳过 / 不可用（可选，不影响规范流程）
```

写入并获得检查结果后报告：

```text
[规范追踪｜写入后]
目标：<文件、类或方法>
确定性检查：通过 / 不通过 / 无适用检查
AI 规范审查：通过 / 仅建议 / 尚未执行
结论：<准确结论，不扩大为“完全合规”>
```

只有检查确实执行并通过时才能写“验证通过”。对于只能由 AI 判断的规则，明确标为“仅 AI 审查”。

## CodeGraph

CodeGraph 不是前置依赖。若当前 Codagent 已提供可用的 CodeGraph 工具，并且查询相似实现、符号关系或影响范围能改善本次修改，可以使用；不可用或没有必要时直接跳过。绝不能虚构查询结果，也不能因 CodeGraph 不可用而跳过规范检索。
